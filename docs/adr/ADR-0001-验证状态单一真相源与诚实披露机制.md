# ADR-0001: 验证状态单一真相源与诚实披露机制

- **状态**:Accepted
- **日期**:2026-09-12
- **决策者**:仓库维护者（见 [AUTHORS.md](../../AUTHORS.md)）
- **知情人**:—

## 背景与问题

2026-09-12 的全局核对确认，公开仓验证体系存在「三层漂移」：代码与 CI 为 v0.5.0（当日四条验证 CI 落地），证据库冻结于 2026-08-18（全部产自 v0.3.1），验证文档冻结于 2026-08-17 且与当前实况多处不符（12 项核对发现，逐项记录于 [verification/DISCLOSURE_LOG.md](../../verification/DISCLOSURE_LOG.md) 首条）。上述漂移的成因是 EvoRule 经历三次大的重构、大量功能（含部分形式化验证资产）移出本仓后公开仓文档未同步；漂移前的记录（含 PASS/FAIL/崩溃）本身为如实记录（见该日志首条漂移根因说明）。验证状态当时分散在 7 处独立声明（原 INDEX §六、白皮书 v3 追溯矩阵、TCB/reactor 的 KANI.md、根 README badge、GATE_REFERENCE.md、ROADMAP.md），彼此矛盾且与实际不符；旧三档状态词汇（✅实跑 / 🔧已实现未跑 / ⏳未实现）无法表达「proof 存在但实测不可运行」等真实状态。需要决定：验证状态由谁权威承载、如何表述、变更如何约束。

## 决策驱动力

- **诚实性**：对外表述必须与实际验证状态一致，历史不掩饰
- **可维护性**：消灭多份状态声明的同步成本（人工同步已被漂移证伪）
- **可追溯性**：证据效力与 proof 代码变更的对应关系需要成文规则
- **披露纪律**：一切偏离留痕，且只记事实

## 候选方案

1. 维持现状：状态继续分散在各文档，靠人工同步
2. 以白皮书 plan v3 为状态真相源（原 INDEX.md §六的规定）
3. 新建 `verification/STATUS.md` 为唯一状态真相源，配套 `MECHANISM.md`（机制规则）与 `DISCLOSURE_LOG.md`（披露日志）

## 决策结果

**选择方案 3**，因为它将「状态、规则、历史」三者分离——STATUS.md 是唯一权威（M1），M1–M11 成文规则约束表述与证据效力，一切偏离进披露日志；方案 1 已被三层漂移证伪，方案 2 让方法论与状态混排于同一长文档、修订成本高且延续第二状态源。

### 后果

- 好的方面：状态一处查询；五档词汇（✅/🟡/🔵/⏳/❌）如实表达真实状态；变更强制披露，与实况不符的表述可定位
- 不好的方面：状态变更需同时更新 STATUS.md 与 DISCLOSURE_LOG.md，多一步操作
- 如何缓解负面影响：两处均为表格式小改，换来的是七处声明同步问题的根除

### 验证方式

- 指标：整改验收清单（check_doc_safety --strict / check_docs_bilingual / 全仓死引用 grep / cargo test 零破坏 / STATUS ↔ README ↔ KANI.md ↔ CI yml 交叉抽查）
- 复盘时间点：每次 release 检查（M4：STATUS 快照版本 = 待发布版本）
- 触发回滚的条件：若 STATUS 更新遗漏持续偏高、维护成本显著超过收益，经新 ADR 废止本决策

## 各方案利弊

### 方案 1

- 优点：零改动
- 缺点：已被实测证伪——七处声明漂移、12 项与实况不符（见 [DISCLOSURE_LOG.md](../../verification/DISCLOSURE_LOG.md) 首条）

### 方案 2

- 优点：不新增文件
- 缺点：白皮书是方法论文档，状态与方案混排；每次状态修正都要动长文档；仍是「文档即真相」的旧模式

### 方案 3

- 优点：状态/规则/历史三分离；五档词汇如实；强制披露
- 缺点：新增两份文档与一步同步操作

# ADR-0001: Single Source of Truth for Verification Status and Honest Disclosure Mechanism

- **Status**: Accepted
- **Date**: 2026-09-12
- **Deciders**: repository maintainers (see [AUTHORS.md](../../AUTHORS.md))
- **Informed**: —

## Background and Problem

A global cross-check on 2026-09-12 confirmed a "three-layer drift" in the public repository's verification system: code and CI at v0.5.0 (four verification CI workflows landed that day), the evidence library frozen at 2026-08-18 (all artifacts produced by v0.3.1), and verification documents frozen at 2026-08-17 and out of sync with current reality in multiple places (12 findings, itemized in the first entry of [verification/DISCLOSURE_LOG.md](../../verification/DISCLOSURE_LOG.md)). The drift stems from three major refactorings that moved substantial functionality, including part of the formal-verification assets, out of this repository without updating the in-repo documents; the pre-drift records (including PASS/FAIL and crashes) were themselves faithfully recorded (see the drift-cause note in that log's first entry). Verification status was scattered across 7 independent declarations (former INDEX §六, whitepaper v3 traceability matrix, TCB/reactor KANI.md, root README badge, GATE_REFERENCE.md, ROADMAP.md), mutually contradictory and out of sync with reality. The legacy three-tier vocabulary (✅ run / 🔧 implemented-not-run / ⏳ not-implemented) could not express real states such as "proof exists but is not runnable in practice". A decision was required on which artifact authoritatively carries verification status, how it is expressed, and how changes are governed.

## Decision Drivers

- **Honesty**: external statements must match actual verification status; no whitewashing of history
- **Maintainability**: eliminate the sync cost of multiple status declarations (manual sync already falsified by the drift)
- **Traceability**: evidence validity versus proof-code changes needs written rules
- **Disclosure discipline**: every deviation leaves a trace, facts only

## Options Considered

1. Status quo: status stays scattered across documents, synced manually
2. Whitepaper plan v3 as the status source of truth (the former INDEX.md §六 rule)
3. New `verification/STATUS.md` as the single status authority, with `MECHANISM.md` (rules) and `DISCLOSURE_LOG.md` (disclosure log)

## Decision Outcome

**Option 3 was chosen**, because it separates status, rules, and history — STATUS.md is the single authority (M1), the M1–M11 written rules constrain expression and evidence validity, and every deviation goes to the disclosure log. Option 1 was falsified by the three-layer drift; Option 2 mixes methodology with status in one long document and perpetuates a second status source.

### Consequences

- Upside: one place to query status; the five-tier vocabulary (✅/🟡/🔵/⏳/❌) expresses real states faithfully; mandatory disclosure makes inconsistent statements locatable
- Downside: status changes require updating both STATUS.md and DISCLOSURE_LOG.md — one extra step
- How the negative effects are mitigated: both edits are small table updates, in exchange for eliminating the seven-way sync problem

### Validation

- Metrics: rectification acceptance checklist (check_doc_safety --strict / check_docs_bilingual / repo-wide dead-reference grep / cargo test zero breakage / cross-check STATUS ↔ README ↔ KANI.md ↔ CI yml)
- Review checkpoint: every release check (M4: STATUS snapshot version == release version)
- Conditions that trigger a rollback: if STATUS update omissions stay high and maintenance cost clearly exceeds benefit, supersede this ADR with a new one

## Pros and Cons of Each Option

### Option 1

- Pros: zero change
- Cons: falsified in practice — seven-way drift, 12 inconsistencies (see the first entry of [DISCLOSURE_LOG.md](../../verification/DISCLOSURE_LOG.md))

### Option 2

- Pros: no new files
- Cons: the whitepaper is a methodology document; status mixed with plans; every status fix touches a long document; still the old "document-as-truth" model

### Option 3

- Pros: separation of status / rules / history; faithful five-tier vocabulary; mandatory disclosure
- Cons: two new documents and one extra sync step
