# EvoRule 形式化验证保证声明（Assurance Case）

> **性质**：本文件是 EvoRule 机制层保证内容的**规范性文件**。它规定「验证什么、验证到什么程度、凭什么、以及在什么前提下成立」。
> **规范地位**：本文件是 EvoRule 机制层保证事务的规范依据。**它约束项目，不被项目状态约束**——项目向本文件对齐，而非本文件向现状让步（§0.4）。
> **不承载状态**：本文件**不含任何**验证状态、数量、达成率、缺口或进度表述。当前实际达成情况一律以 [STATUS.md](STATUS.md) 为准（[MECHANISM.md](MECHANISM.md) M1）。
> **适用对象**：EvoRule 机制层四仓（`evorule-tcb` / `evorule-reactor` / `evorule-governance` / `evorule-cli`）。
> **版本对齐**：见 [MECHANISM.md](MECHANISM.md) M4。
> **版本**：v1.0。首次成文 2026-09-17。修订程序见 §0.6，修订历史见附录 D。

## 第 0 章 文件性质、效力与修订

### 0.1 这是什么，不是什么

本文件是一份**保证案例（Assurance Case）**，采用业界通行的三段结构（参照 seL4 的 proof statements / assumptions / non-claims 组织方式，以及 GSN 的 Claim–Argument–Evidence 论证结构）：

| 段落 | 内容 | 对应章节 |
| ---- | ---- | -------- |
| **主张（Claims）** | 系统对外承诺什么，承诺的精确含义 | 第 3 章 |
| **论证（Arguments）** | 主张如何分解为可验证的子命题 | 第 4 章 |
| **证据（Evidence）** | 每个子命题凭什么成立、由何种手段产生 | 第 2、4、8 章 |
| **前提（Assumptions）** | 主张在什么前提下才成立 | 第 5 章 |
| **限度（Non-Claims）** | 明确**不**承诺什么 | 第 6 章 |

**本文件不是**：

- 不是营销材料。本文件的一切表述受 §0.7 约束。
- 不是验证状态表。状态见 [STATUS.md](STATUS.md)。
- 不是验证方案（怎么做）。方案见 [plan/](plan/) 与各 crate 验证设计文档。
- 不是变更或偏离记录。变更与偏离见 [DISCLOSURE_LOG.md](DISCLOSURE_LOG.md) 与 [STATUS.md](STATUS.md)。
- 不是安全评估报告或认证证书。EvoRule **未申请**任何行业认证（NC-14）。

### 0.2 读者与用途

| 读者 | 用途 |
| ---- | ---- |
| **形式化方法专家 / 外部审计方** | 审查主张是否成立、论证链是否完整可追溯、假设是否被充分披露 |
| **合规与监管方**（金融、医疗、政务等保、AI 治理） | 判断本验证证据能否支撑其合规目标；识别需自行补足的部分 |
| **集成方 / 架构决策者** | 判断 EvoRule 的保证边界是否覆盖其风险面；明确自身须承担的保证责任 |
| **项目内部** | 作为验证工作的目标轮廓与验收基准；**偏离本文件的每一项都须登记（§4.3）** |

### 0.3 效力与效力分层

**规范效力**：本文件对 EvoRule 机制层的**对外保证内容**具有规范效力。任何对外材料（README、发布说明、集成指南、商务材料）中的保证类表述，**应**能追溯到本文件的某条声明；无法追溯的保证类表述**不得**发布。

**效力分层**（对照 ISO/IEC 导则的规范性 / 资料性划分）：

| 章 / 附录 | 性质 | 含义 |
| --------- | ---- | ---- |
| §0.1–§0.2 | **资料性** | 文件性质说明与读者指引；不产生保证义务 |
| §0.3–§0.7 | **规范性** | 本文件自身的效力、准入与修订规则 |
| 第 1–8 章 | **规范性** | 构成保证承诺；偏离即须登记（§4.3），变更须走 §0.6 的 B 类程序 |
| 第 9 章 | **资料性** | 方法论来源与外部对照；不构成承诺，也不构成符合性主张 |
| 附录 A–D | **资料性** | 术语、索引、质询应答、修订史；不构成承诺 |

**规范性条款**以「应」「不得」「是」表述；**资料性内容**不产生义务，其更新属编辑性变更。

### 0.4 规范与状态的分离（本文件的规范地位）

**本文件规定「应达到什么」；[STATUS.md](STATUS.md) 记录「已达到什么」。二者严格分离，且分离是强制的。**

**禁令**：

1. 本文件**不得**出现任何验证状态、数量、百分比、达成率、缺口清单或进度表述；
2. 本文件**不得**为使自身与项目现状一致而修订——现状变化**不是**修订理由（§0.6）；
3. 任何对外材料**不得**把本文件第 3 章的目标等级表述为已达成等级；已达成的项由 [STATUS.md](STATUS.md) 提供（[MECHANISM.md](MECHANISM.md) M1、M6）。

**理由**：一份随项目进度而频繁改动的声明文件无法承担承诺功能——读者无法区分「承诺变了」与「只是进度变了」，声明因而失去公信力。承诺的稳定性是承诺有效性的前提。因此本文件的对齐方向是单向的：**项目向本文件对齐。**

### 0.5 条款准入：时效不变量测试与禁止写入清单

任何拟写入本文件的条款，**应**先通过以下三项测试（Time-Invariance Test, TIT）。**任一项不通过者，不得写入本文件**，应写入 [STATUS.md](STATUS.md)（状态类）或 [ROADMAP.md](../ROADMAP.md) / [DISCLOSURE_LOG.md](DISCLOSURE_LOG.md)（计划与变更类）。

| # | 测试 | 不通过的情形 |
| - | ---- | ------------ |
| **TIT-1 完成测试** | 若该条款所要求的工作**全部完成**，该条款是否仍然成立？ | 「完成后即失效」的条款是状态，不是规范 |
| **TIT-2 变更测试** | 若实现、证据、进度、里程碑发生变化，该条款是否需要改写？ | 「需随现状改写」的条款属于状态 |
| **TIT-3 证伪测试** | 该条款是否可被某个具体的反例形态证伪？ | 不可证伪者不是声明，是意图描述 |

**禁止写入清单**（上述测试的操作化，可部分通过文本检索核查）：

| 禁止内容 | 归属位置 |
| -------- | -------- |
| 验证状态、数量、百分比、达成率、「已完成/已修复/已退役」 | [STATUS.md](STATUS.md)、[DISCLOSURE_LOG.md](DISCLOSURE_LOG.md) |
| 「当前缺口 / 尚未落实 / 现状是 / 目前止于」式偏离叙述 | [STATUS.md](STATUS.md)（偏离登记，§4.3） |
| 里程碑、排期、版本计划、攻坚目标 | [ROADMAP.md](../ROADMAP.md)、`verification/plan/` |
| commit SHA、证据文件名、时间戳、实跑耗时 | 证据归档与 [STATUS.md](STATUS.md) |
| 与其他系统或标准的比较结论 | 禁止（§0.7） |
| 内部知识库的路径、目录名、文件名或内容 | 禁止（[MECHANISM.md](MECHANISM.md) M9） |
| 个人身份信息 | 禁止（[MECHANISM.md](MECHANISM.md) M11） |

### 0.6 修订程序

**修订分类**：

| 类别 | 触发条件 | 版本号 | 附加要求 |
| ---- | -------- | ------ | -------- |
| **A 类 · 编辑性** | 错别字、链接失效、术语统一、不改变语义的表述澄清；资料性附录的更新 | `x.y → x.y+1` | 无需影响评估；不得借编辑性修订改变规范语义 |
| **B 类 · 规范性** | 声明集合增删、声明措辞收紧或放宽、目标等级升降、保证等级定义或判定规则变更、假设增删、不保证事项增删、本文件效力条款变更 | `x.y → (x+1).0` | ① 影响评估（列出受影响的既有证据与对外材料）；② 按 [MECHANISM.md](MECHANISM.md) M5 记入 [DISCLOSURE_LOG.md](DISCLOSURE_LOG.md)；③ 全文一致性与链接检查 |
| **C 类 · 承诺降级** | 某条声明的**目标等级下调**，或某条声明被删除 | 走 B 类程序，且**加严** | 除 B 类要求外，**应**说明：理由（不可达 / 成本失衡 / 属性本质不归该等级）、被放弃的性质的替代处置、以及该放弃是否需转为不保证事项（第 6 章）。与新增不保证事项同等严肃 |

**修订理由（穷尽列举）**：仅下列情形构成修订理由——

1. 本文件**自身存在缺陷**：内部矛盾、不可证伪的条款、范围遗漏、等级定义不可度量、与上位机制文档（[MECHANISM.md](MECHANISM.md)）冲突；
2. 系统**对外承诺内容**发生实质变化（产品定位变化、边界重划）；
3. 外部现实变化使某条声明不再可判读（如所参照的标准被废止）。

**明确不构成修订理由**（重要）：

| 非理由 | 正确处理 |
| ------ | -------- |
| 项目取得进展；某条声明的目标等级已达成 | 只更新 [STATUS.md](STATUS.md) |
| 某条偏离被消除 | 只更新 [STATUS.md](STATUS.md) 偏离登记 |
| 工具链 / 验证工具 / 依赖版本升级 | 只更新证据元数据与状态 |
| 某项证明不可运行或耗时变化 | 只更新 [STATUS.md](STATUS.md)（按规则 R3 处置） |
| 里程碑、排期、优先级变化 | 更新 [ROADMAP.md](../ROADMAP.md) 与 `verification/plan/` |
| 对外沟通或表述便利 | **不得**为此修订规范条款 |

**修订频次纪律**：规范条款的修订**应**保持稀少。A 类修订**应**合并发布（不做逐字级刷版本）；任何版本号变更**应**在附录 D 留痕，且**应**能对应上表某一类修订理由。

### 0.7 对外表述纪律

**本文件与一切对外材料不得使用未限定的比较级表述**（如「超过 X 的等级」「强于 Y 的要求」）——依据 [MECHANISM.md](MECHANISM.md) M6.3。理由有二：

1. **口径不可比**：不同体系的等级衡量的是不同东西（过程保证 vs 命题证据），比较缺乏共同分母；
2. **事实基础不足**：比较级表述要求对**两侧**都有充分证据；对他方体系，其完整要求并非本仓可充分评估的对象。

**可以做的表述**：说明使用了哪些方法、这些方法在各体系中的**对应位置**（第 9 章）、以及自身证据的达成情况（引用 [STATUS.md](STATUS.md)）。**不可以做的表述**：声称超越或等同任何体系的等级。

## 第 1 章 系统定义、责任边界与威胁模型

> **本章目的**：保证声明的第一原则是**不越界**。任何未界定系统边界与责任划分的保证声明，在专家审查中都会因"责任范围不清"而被质疑。本章先把边界钉死。

### 1.1 系统是什么（可反驳的定义）

**EvoRule 是一个确定性的 JSON 规则执行引擎。** 它接收三样东西——规则集（JSON）、初始状态（JSON）、外部事件序列（JSON）——按可重放、可审计的方式推进状态机，产出状态变更序列与一份带哈希链的事实账本。

**EvoRule 不是**（这些否定同样是定义的一部分）：

| 不是 | 因为 |
| ---- | ---- |
| 不是 LLM / AI 系统 | 机制层零 AI、零 LLM、零 embedding、零"推理" |
| 不是通用工作流引擎 | 控制流由 JSON 规则在运行时决定，不是预定义步骤序列 |
| 不是数据库 | 事实账本是 append-only 事件流，不是关系型存储 |
| 不是分布式系统 | 核心仓是单进程反应器；多反应器协作在应用层 |
| 不是策略/规则语言 | 它不提供 DSL，只接受 JSON；规则的正确性由使用者负责（见 §1.3） |

**这个定义的可反驳点**：若发现机制层任何组件引入了系统时间、随机数、浮点、线程调度依赖，或引入 LLM 调用，则该组件不属于 §1.2 定义的机制层，本文件的保证不延伸至它。

### 1.2 系统边界：机制层与应用层

本文件的保证**只覆盖机制层**：

| 层 | 组件 | 是否在本声明范围 |
| -- | ---- | --------------- |
| **机制层** | `evorule-tcb`（执行内核）、`evorule-reactor`（反应器 / 账本 / WAL）、`evorule-governance`（审计 / 时间机器 / 守卫 / 会话 / 签名） | 在范围内 |
| 工具层 | `evorule-cli`（参数解析、输出格式化） | 不在范围（其依赖的机制层接口在范围） |
| 应用层 | HTTP API、SSE、认证中间件、指标导出、具体 I/O Handler 实现、热重载、SDK | 不在范围 |

**边界规则**：机制层不包含 HTTP、SSE、Prometheus、Bearer 认证、具体 I/O Handler 实现。这些由应用层自建。**机制层提供接口与语义，不提供实现。**

**实践含义**：应用层的缺陷（路由错误、认证绕过、SSE 序列化错误）**不在**本声明的保证范围内，本文件不对其作任何保证。集成方须自行对应用层独立验证。

### 1.3 责任分配（共享责任模型）

这是本文件**最重要的一节**。行业实践表明（参照 AWS Cedar 的共享责任模型），形式化验证系统的绝大多数争议源于责任边界模糊。EvoRule 明确划分：

| 事项 | EvoRule 负责 | 使用者负责 |
| ---- | ------------ | ---------- |
| **引擎语义**：给定规则集与输入，引擎按规范执行 | 全部 | — |
| **执行确定性**：同输入同输出 | 全部 | — |
| **失败行为**：畸形输入不产生未定义失败 | 全部 | — |
| **账本完整性**：哈希链的可篡改检测 | 全部 | — |
| **守卫强制**：机制层判定点的不可绕过性 | 全部 | — |
| **规则/策略正确性**：规则是否实现了你的业务意图 | **不负责** | **全部** |
| **调用正确性**：是否调用了守卫判定点、是否装配了守卫 | **不负责** | **全部** |
| **输入规模控制**：是否限制规则集/输入体积 | **不负责** | **全部** |
| **I/O Handler 实现**：外部系统的实际行为与可用性 | **不负责** | **全部** |
| **部署配置**：构建 feature 组合、运行环境、密钥管理 | 不负责（但须提供可检测信号） | **全部** |
| **应用层**：HTTP/SSE/认证/前端 | 不负责 | **全部** |

**两条必须被读到的推论**：

1. **「引擎验证通过」≠「系统安全」。** 一个被证明正确的引擎，可以被错误配置、被传入错误规则、被绕过守卫而使用，其后果不由本声明承担。这与 seL4 的公开立场一致：形式化验证的微内核不自动使系统安全。
2. **守卫的强制性有一个前提：调用路径必须经过判定点。** 机制层保证「判定点本身不可绕过」，但「是否调用判定点」在应用层。因此 §3.6 的声明附带一项**义务**：机制层**应**提供可检测信号，使「守卫未被装配」这一状态可被外部观测（详见 §3.6 条款 5 与附录 B）。

### 1.4 威胁模型

保证声明的强度只有在明确敌手后才有意义。本声明的敌手模型：

| 维度 | 假定 |
| ---- | ---- |
| **敌手能力** | 能构造**任意** JSON 输入（畸形、超深、超大、含恶意规则）；能构造任意外部事件序列 |
| **敌手位置** | 在机制层之外（进程外/应用层）；能控制输入与 I/O 应答 |
| **敌手不能** | 修改机制层进程内存；修改已验证的源码；替换构建产物（这些属于供应链威胁，见 §5） |
| **账本敌手** | 能读取并**改写**账本文件（拥有文件系统写权限）；不能伪造签名密钥 |
| **不在模型内** | 侧信道 / 时序攻击；物理攻击；硬件故障注入；编译器/供应链投毒；操作系统内核漏洞 |

**术语约定**：本文件中的"任意输入"一律指**敌手可构造的任意 JSON 输入**，除非条款另有说明。凡以"任意输入"表述的声明，其成立不依赖输入的规模、深度、形状。

## 第 2 章 保证等级（Assurance Levels）

> **本章目的**：回答"证明到什么程度"。核心洞见是：**验证的强度不由使用的工具决定，而由（命题的强度 × 证据的强度 × 验证对象与交付物的一致程度）三者共同决定。**

### 2.1 为什么需要一个等级体系

现有的两值表述（"已证明 / 未证明"）无法承载真实情况，其后果是：

- 把「抽样测试通过」与「机器核验证明」并列，导致对外声明失真；
- 把「在替身上证明」与「在生产代码上证明」并列，导致保证对象错位；
- 把「界内穷尽」与「无界成立」并列，导致保证强度不明。

因此 EvoRule 采用五级保证等级。**等级是对"证据强度 + 对象同一性"的联合刻画，不是对工具的名称映射。**

### 2.2 等级定义

| 等级 | 名称 | 判定条件（须全部满足） | 典型证据形态 | 该等级**不**主张 |
| ---- | ---- | ---------------------- | ------------ | ---------------- |
| **AL0** | 意图（Stated） | 命题以自然语言明确陈述，且**可证伪**（能想象出反例形态） | 本文件章节、设计规范 | 不主张任何机器证据 |
| **AL1** | 抽样（Sampled） | 在有限输入样本上执行通过；样本来自随机生成或人工构造；结论具统计意义 | 单元测试、属性测试（proptest）、模糊测试（fuzz） | 不主张穷尽；不主张样本外成立 |
| **AL2** | 界内穷尽（Bounded-exhaustive） | 在**显式声明的界**（循环展开深度、输入形状约束、状态数、参数取值）内穷尽所有可达路径；界外**不主张**；且须证明界本身足够（展开断言不失败） | 有界模型检测（Kani / CBMC）、显式状态模型检测（TLC） | 不主张界外成立；不主张界的选择是完备的 |
| **AL3** | 机器核验证明（Machine-checked） | 命题对**无界**或**参数化**的输入域成立，由机器核验其推导，无"未检查的人工推理"环节 | 演绎验证（Verus / Coq / Lean）、带函数合同与循环合同的模型检测 | 不主张验证对象等于生产交付物 |
| **AL4** | 生产载体核验证明（Machine-checked on Production Artifact） | 满足 AL3，**且**证明所覆盖的代码在**生产构建配置下与交付物逐字等同**：无 `cfg` 分叉替换被验证的行为、无仅在验证配置下生效的常量改写、无可观测行为差异 | AL3 的证据 + 载体同一性证据（构建配置比对 + 差分验证） | 不主张规格正确；不主张下游二进制等价（除非另有二进制级证据，见 NC-16） |

### 2.3 等级的四条判定规则（关键）

**规则 R1（载体优先原则）**：若验证配置下被验证的代码与生产配置下执行的代码**行为不等同**，则该证据的最高等级为 **AL2**，无论其证明技术多强、命题多漂亮。理由：保证是对**交付物**的保证，不是对**某个模型**的保证。

> 这条规则是本保证体系的基石。它把"被验证对象是否就是产品"从工程细节上升为等级判据。

**规则 R2（界必须声明原则）**：AL2 的证据**必须**显式声明其界（展开深度、形状约束、参数取值）。未声明界的 AL2 证据，按 AL1 计。

**规则 R3（超时必须保守原则）**：验证工具返回「未知 / 超时」时，**不得**解释为通过；且系统在该属性上的运行时行为**应**取向保守侧（拒绝、降级为安全态、或显式报错），不得取向放行侧。（该原则的行业依据见 §9.1。）

**规则 R4（规格非免证原则）**：任何等级都**不**保证规格本身正确。规格是人的产物；AL3/AL4 证明的是「实现符合规格」，不是「规格符合意图」。这与 seL4、CompCert 的公开立场一致。

### 2.4 目标保证轮廓（Target Assurance Profile）

下表定义**每条顶层声明的目标等级**。这是 EvoRule 对"证明到什么程度"的正式回答，属**规范条款**。**实际达成等级不在本文件，见 [STATUS.md](STATUS.md)**。

| 声明 | 目标等级 | 目标等级的理由 |
| ---- | -------- | -------------- |
| C1 执行确定性 | **AL4** | 确定性是产品的第一性承诺；若验证对象 ≠ 生产对象，该承诺无意义 |
| C2 无未定义失败 | **AL4**（核心路径）/ AL3（全量） | 敌手可构造任意输入，需覆盖全输入域；全量 AL4 成本高，核心路径优先 |
| C3 执行有界 | **AL3**（参数化）/ AL2（具体配置） | 上界应作为参数证明（对所有限值成立），而非只证某个具体常量 |
| C4 审计不可篡改 | **AL3** + AL1（实现） | 链式哈希的结构性质可演绎证明；具体哈希实现依赖库正确性（假设 H3.1） |
| C5 重放忠实 | **AL3** + AL1（端到端差分） | 重放忠实可由 C1+C4 推出其主体，端到端以差分测试佐证 |
| C6 守卫强制 | **AL4** | 守卫是产品根本契约；若判定点可被绕过或未装配，声明即失效 |
| C7 规则静态安全性 | **AL2 + AL1** | 静态分析的健全性（soundness）可界内穷尽验证；完备性明确不主张 |

**目标等级的推进方向**（等级的定义性阶梯，不含任何项目进度信息）：

```
AL0 ──▶ AL1 ──▶ AL2 ──▶ AL3 ──▶ AL4
意图    抽样    界内穷尽   机器核验   生产载体核验
                              ▲
                              └── AL3→AL4 的跨越以「载体同一性」为唯一判据（规则 R1）：
                                  验证配置与生产配置的行为一致性
                                  是这一级晋升的必要条件
```

### 2.5 目标等级的可接受性判据

一条声明的目标等级是否"足够"，取决于其**失效后果**。EvoRule 采用的判据是：

- 失效会导致**安全边界失守**（守卫被绕过、账本被伪造）→ 目标 **AL4**
- 失效会导致**决策结果错误**（不确定性、静默失败）→ 目标 **AL4**（核心）/ AL3（全量）
- 失效会导致**服务异常**（不终止、崩溃）→ 目标 **AL3**
- 失效仅影响**效率或体验**（性能、格式）→ 目标 AL1，不做形式化主张

**目标等级的降级受 §0.6 C 类程序约束**：下调目标等级属承诺降级，须说明理由与替代处置。

## 第 3 章 顶层保证声明（Claims）

> **本章是保证内容的主体。** 每条声明包含七个固定字段：命题、精确化、工程含义、目标等级、证据形式、依赖假设、失效条件。
> **措辞约定**：「对于……成立」为**事实断言**（可被反例证伪）；「应」「不得」为**规范义务**（对实现的约束）。

### 3.1 C1 · 执行确定性

**命题**
对于任意两个执行 $e_1$、$e_2$，若二者接收**相同的输入三元组**——相同的规则集快照、相同的初始状态、相同的外部事件与 I/O 应答序列——则二者产生的**输出三元组**（状态变更序列、最终状态、账本哈希链）逐字节相同。

**精确化**
- "外部事件与 I/O 应答序列"被**建模为输入**。这是本声明的关键设计：EvoRule 不承诺"排除外部世界的多样性"，而是承诺"把外部世界的多样性收敛为显式输入"。因此 I/O 的时序、内容差异**不构成**确定性反例——只要它们作为应答序列被记录。
- "逐字节相同"要求输出序列化形式唯一（字段顺序、数值表示、字符串转义均确定）。
- 声明**不**要求执行时间、内存占用、CPU 指令数相同。

**工程含义（对应实现约束）**
实现**不得**在机制层引入：系统时间、随机数、浮点数、哈希容器迭代顺序依赖、线程/异步调度、全局可变状态。这些是**可静态检查的**（构建期门禁可枚举禁止模式）。

**目标等级**：AL4。

**证据形式（多重独立手段，任一单手段均不足以支撑）**

| 手段 | 覆盖 | 等级 |
| ---- | ---- | ---- |
| 构建期禁止模式门禁 | 禁止项的存在性（时间/随机/浮点/容器/线程） | 可判定的静态证据 |
| 符号执行的确定性断言 | 相同输入下两次执行路径等价 | AL2（界内）/ AL3（含合同） |
| 属性测试 | 随机输入的输入-输出确定性 | AL1 |
| 差分测试（同一逻辑的两条实现路径对比） | 实现间一致性 | AL1 |
| 容器序与序列化唯一性测试 | 迭代顺序、序列化唯一性 | AL1 |

**依赖假设**：H1.1（编译器不改变算术与容器语义）、H3.2（依赖 crate 的确定性）、H4.1（生产构建配置无行为级分叉）。

**失效条件（何时这条声明不再成立）**
1. 任何机制层代码引入时间 / 随机 / 浮点 / 线程 / 哈希迭代序依赖；
2. 被验证代码与生产代码存在**行为级**配置分叉（按 R1 降级）；
3. 依赖 crate 在版本升级中引入非确定性行为。

### 3.2 C2 · 无未定义失败

**命题**
对于任意输入（含任意畸形 JSON、任意嵌套深度、任意字节序列），机制层**不产生**：panic、未定义行为、越界访问、整数溢出或回绕、未处理的 `Result::Err`、静默截断、无限阻塞。所有不可处理的输入**应**以显式错误值返回（错误类型 / 错误事实），且该错误本身是确定性的（受 C1 约束）。

**精确化**
- 「不 panic」在 Rust 中可静态约束（禁止 `unwrap` / `expect` / 索引切片 / `panic!` / `unreachable!` / `todo!` / `unimplemented!` / `exit` / 显式 `mem::forget` 泄漏）。
- **算术语义必须显式声明**：Rust 在 debug 构建下对整数溢出 panic，在 release 构建下**静默回绕**。静默回绕比 panic 更危险（产生错误结果而不报错）。因此本声明要求：机制层的算术**应**使用显式受检运算（`checked_*` / `saturating_*`）并显式处理溢出，**不得**依赖构建配置的溢出检查策略。这一要求的证据必须覆盖**两种构建配置**。
- 声明**不**覆盖资源耗尽（内存不足、文件系统满）。资源耗尽属于环境故障，见 §6 不保证事项与 §5 环境假设。

**目标等级**：核心执行路径 AL4；全量 AL3。

**证据形式**

| 手段 | 覆盖 | 等级 |
| ---- | ---- | ---- |
| 编译期 lint 门禁（禁 panic 源 + 受检算术） | 禁止构造的存在性 | 可判定的静态证据 |
| 符号执行（never-panic 属性，全输入域） | 分支 panic 自由 | AL2/AL3（视界与合同） |
| 属性测试 + 模糊测试 | 随机/演化输入下的存活 | AL1 |
| 双重构建配置验证 | debug 与 release 行为一致 | AL1（一致性证据） |

**依赖假设**：H1.1、H1.2（验证工具对 panic/UB 的建模正确）、H1.3（lint 规则覆盖全部 panic 源）。

**失效条件**
1. 引入新的 panic 源（包括间接：索引、除零、`unwrap`、库函数 panic）；
2. 引入裸算术而未经受检运算；
3. 生产构建使用 `panic = "abort"` 等改变失败语义的配置而未在声明中记录；
4. 验证工具对某类 UB 不支持（工具能力边界，见 §7）。

### 3.3 C3 · 执行有界

**命题**
存在一组**有限的、可静态检查的**上界 $(D_{branch},\ D_{domain},\ N_{steps},\ N_{rules})$，使得：
1. 任意单次状态转换在至多 $N_{steps}$ 步内终止；
2. 任意递归/嵌套求值的深度不超过对应上界；
3. 单次转换应用的规则数不超过 $N_{rules}$；
4. 超出上界的输入被**显式拒绝**（返回确定性错误），**不得**继续执行、**不得**崩溃、**不得**静默截断。

**精确化**
- 上界**应**以**参数**形式存在并参与证明（证明"对所有合法限值成立"），而非仅在证明中硬编码某个具体常量。理由：若证明只对某个具体常量成立，则该证明对生产配置的另一个常量**不提供任何保证**。
- "显式拒绝"是声明的组成部分：**仅有上界而无拒绝机制不构成终止性保证**。

**目标等级**：参数化形式 AL3；具体配置 AL2。

**证据形式**

| 手段 | 覆盖 | 等级 |
| ---- | ---- | ---- |
| 符号执行（深度/步数上界属性，参数化） | 任意输入下不超过上界 | AL3（参数化）/ AL2（具体值） |
| 显式状态模型检测（状态机不变式） | 状态可达性与转移合法性 | AL2（有限模型） |
| 属性测试 | 深/宽输入的拒绝行为 | AL1 |

**依赖假设**：H1.2、H4.1（生产配置的上界值与证明中的一致）。

**失效条件**
1. 上界常量变更而未重跑证据（证据失效，见 §8.2）；
2. 新增构造路径绕过上界检查（如新增递归调用而未受深度参数约束）；
3. 拒绝机制被移除或改为静默截断。

### 3.4 C4 · 审计不可篡改

**命题**
事实账本是 append-only 的哈希链。对于任意历史条目，在账本被读取时，任何对其**内容**的修改、**删除**、**插入**、**重排**，都会导致完整性验证失败。

**精确化（必须逐字读到）**
- 本声明主张的是 **tamper-evident（篡改可检测）**，**不是 tamper-proof（不可篡改）**。持有账本文件写权限的敌手**可以**整体重写账本，但必须重算全链。
- 若账本已被**外部锚定**（签名、外部时间戳、异构存储），则整体重写亦不可行——但该保护强度取决于锚定机制，锚定本身不在本声明范围（签名机制见 `evorule-governance/src/signing.rs`，其正确性依赖 H3.1 密码学库假设）。
- 声明**不**覆盖：账本从未写入（写入失败）、写入后被截断、存储介质损坏。写入失败的处理策略（连续失败达阈值即终止会话，fail-closed）属于实现行为，其正确性是 C2 与 C3 的对象。

**目标等级**：结构性质 AL3 + 实现 AL1。（结构性质可演绎证明；具体哈希实现依赖库正确性。）

**证据形式**

| 手段 | 覆盖 | 等级 |
| ---- | ---- | ---- |
| 哈希链结构性质的演绎/归纳证明 | 篡改必然破坏链 | AL3 |
| 篡改类属性测试（内容/链哈希/前链哈希三类） | 实现层面可检测 | AL1 |
| 端到端审计链测试 | 全流程 | AL1 |
| 跨实现哈希一致性测试 | 三层（reactor/governance/cli）算法一致 | AL1 |

**依赖假设**：H3.1（哈希函数实现的正确性与抗碰撞性）、H2.2（账本存储的可见语义）。

**失效条件**
1. 哈希算法、链构造方式、或序列化形式变更；
2. 引入可绕过链的写入路径（如"直写文件"分支）；
3. 密码学依赖 crate 版本变更。

### 3.5 C5 · 重放忠实

**命题**
对于任意账本前缀，从初始状态重放该前缀所得的最终状态，与原始执行到该前缀末尾时的状态**逐字节相同**。

**精确化**
- 本声明是"时间机器"能力（回放、回退、分叉、差分）正确性的基础。
- 重放忠实**依赖** C1（确定性）与 C4（账本完整）。若 C1 或 C4 失效，C5 不成立。
- 「状态」的比对范围**应**明确定义（含哪些字段、是否含内部计数器、是否含 I/O 待处理队列），并保持一致。比对范围的定义本身属于规格，不在保证之内（规则 R4）。

**目标等级**：AL3（由 C1+C4 推导的主体）+ AL1（端到端）。

**证据形式**

| 手段 | 覆盖 | 等级 |
| ---- | ---- | ---- |
| 由 C1 + C4 的推导 | 主体性质 | AL3（条件性） |
| 重放差分测试（重放状态 vs 原始账本状态） | 端到端 | AL1 |
| 多会话隔离测试 | 隔离性 | AL1 |

**依赖假设**：C1、C4 成立；H4.1（重放使用的构建配置与原始执行一致）。

**失效条件**
1. 状态序列化形式变更而未同步重放逻辑；
2. C1 或 C4 失效；
3. 重放走的代码路径与原始执行不同（例如重放时跳过守卫检查）。

### 3.6 C6 · 守卫强制（最高优先级声明）

**命题**
机制层中存在一个**判定点**，使得：
1. **不可绕过性**：受守卫保护的动作，无法通过机制层的任何其他公开接口达到同等效果；
2. **失败方向**：判定点在无法作出明确允许判断时，结果**应**为**拒绝**（fail-closed），且该拒绝是确定性的；
3. **决策可追溯**：每次判定产生可审计记录（含判定输入与结果），使判定过程可事后复核；
4. **篡改可检测**：守卫判定所依据的权限表，其变更本身经过账本（因而受 C4 保护）；
5. **装配可检测（义务）**：机制层**应**提供可检测信号，使「判定点未被装配」或「未被调用」的状态**可被外部观测**。

**精确化**
- 条款 1 的"其他公开接口"指机制层 `pub` API 全集，**不含**应用层自建接口。
- 条款 5 的工程背景：机制层可以保证"判定点本身正确且不可绕过"，但"是否调用判定点"在应用层（见 §1.3）。若该状态不可观测，则一个未装配守卫的部署在**外部看起来**与一个正常部署无异——这构成实质风险。因此本条将其规定为**义务**。
- 声明**不**主张：「守卫的判定规则是否符合你的安全策略」——那是使用者责任（§1.3）。

**目标等级**：AL4。

**证据形式**

| 手段 | 覆盖 | 等级 |
| ---- | ---- | ---- |
| 判定逻辑的穷尽决策表验证（枚举输入组合） | 判定正确性 | AL2（有限域）/ AL3（符号输入） |
| 接口可达性分析（枚举 `pub` API 对受保护状态的写路径） | 不可绕过性 | 静态分析 + AL2 |
| 默认拒绝方向的符号验证 | 失败方向 | AL2 |
| 守卫装配可观测性测试 | 条款 5 | AL1 |
| 权限表经账本变更的链路测试 | 条款 4 | AL1 |

**依赖假设**：H6.2（使用者正确调用）；H4.1（生产配置下守卫的装配状态须可检测——此为使用者责任，机制层提供信号）。

**失效条件**
1. 新增绕过判定点的写路径（新 public API、新的直接状态修改入口）；
2. 默认值由「拒绝」改为「允许」；
3. 守卫装配可观测信号被移除，或信号本身不可靠；
4. 权限表存在不经账本的修改路径。

### 3.7 C7 · 规则静态安全性

**命题**
对于任意规则集，机制层的规则验证能力**应**判定其是否包含下列形态，并对命中者给出拒绝：
1. 必然无限循环的规则结构；
2. 无界的中间结果增长；
3. 无界的外部请求生成。

**精确化（方向性必须明确）**
- 本能力主张**健全性（soundness）**：**不**接受不安全规则集；**不**主张**完备性（completeness）**：**可能**拒绝安全规则集。即允许假阳性，不允许假阴性。
- 该方向性选择是刻意的：在安全关键场景中，误拒的代价（人工复核）远低于误纳的代价（放行危险规则）。
- 判定所依据的条件本身属于规格（规则 R4）。

**目标等级**：AL2（界内穷尽）+ AL1（样本）。

**证据形式**

| 手段 | 覆盖 | 等级 |
| ---- | ---- | ---- |
| 判定逻辑的界内穷尽验证 | 判定正确性 | AL2 |
| 已知危险规则集的检测测试 | 检出率 | AL1 |
| 假阳性样本测试 | 完备性的**实测记录**（不构成完备性保证） | AL1 |

**依赖假设**：H6.1（规则集的语义由使用者定义）。

**失效条件**
1. 判定规则变更；
2. 新增规则形态而未被分析覆盖（可能产生假阴性——**直接违反健全性**）。

## 第 7 章 工具信任基（Trust Base）

> **本章目的**：诚实呈现"证明依赖哪些未被证明的东西"。这是保证声明中最容易被忽略、也最容易被专家一击命中的部分。

### 7.1 信任基的定义

**信任基（Trusted Base）** = 为使第 3 章某项声明成立，**必须假定其正确、但本仓未提供其正确性证据**的全部组成部分。

信任基越小、越成熟、越被广泛审查，保证越强。因此下列原则**应**被遵守：

- **原则 T1**：能用更小信任基达成的证据，**应**优先于用更大信任基达成的证据（即使后者更易获得）。
- **原则 T2**：信任基的每一项**应**被显式登记，不得隐式依赖。
- **原则 T3**：新增依赖若扩大信任基，**应**在变更记录中标注其对声明的影响。

### 7.2 信任基登记

| 层 | 组件 | 影响的声明 | 备注 |
| -- | ---- | ---------- | ---- |
| **编译层** | Rust 编译器 + LLVM 后端 | 全部（生产二进制） | 与所有 Rust 项目共享；本仓无额外缓解 |
| **验证层** | 有界模型检测器及其到求解器的翻译链路 | C1、C2、C3、C6、C7 的 AL2 证据 | 按 R1 限定，不含对象同一性 |
| **验证层** | SMT / SAT 求解器 | 同上 | 求解器正确性不由本仓验证 |
| **验证层** | 证明检查内核（当某条声明的证据采用演绎证明时） | C4、C3 的 AL3 证据 | 演绎证明的信任基显著小于模型检测（见 §7.3） |
| **运行时** | 密码学库实现（哈希、签名） | C4、C5 | 性质不可由本仓验证（H3.1） |
| **运行时** | 序列化库、集合库等其余依赖 | C1、C2 | 依赖面**应**最小化 |
| **平台** | 操作系统、文件系统、硬件 | 全部 | 按 H2 假设 |

### 7.3 关于信任基的一个重要工程判断

模型检测类证据（AL2）的信任基**显著大于**演绎证明类证据（AL3）：前者需信任「源码 → 中间表示 → 公式 → 求解器」的整条链路，后者只需信任一个较小的证明检查内核。

这一差异带来的**工程取向**：

- 对于**结构性质**（如链式哈希的单射性、上界参数的不变性），**应**优先考虑演绎证明——其信任基更小，且命题可参数化。
- 对于**输入域性质**（如全输入域的 panic 自由），模型检测在**界内**是当前最经济的手段；但须明确界（R2），且界外转入其它手段。
- **不建议**为追求"没有界"而引入超出长期维护能力的证明工程量——一个无人能维护的证明，其价值低于一个被持续重跑的有界证据。

### 7.4 信任基的不可核查性

**H1.4 假设明确承认：信任基的正确性不可由本仓核查。** 本声明不试图掩盖这一点。行业通行做法是：把信任基**缩小**、**固化版本**、**公开登记**，使其成为可审查对象，而不是消灭它。本文件采用同一立场。

## 第 8 章 证据生成、归档与失效

> **本章不重复 [MECHANISM.md](MECHANISM.md) 的机制条款**（M1–M11 为规则 SSOT），只规定本声明**特有的**要求。

### 8.1 证据的最低要求（本声明附加）

除 [MECHANISM.md](MECHANISM.md) M3 的证据规范外，支撑本声明的证据**应**额外记录：

| 字段 | 用途 | 对应等级判定 |
| ---- | ---- | ------------ |
| **验证对象标识** | 被验证的确切代码（commit SHA + 文件路径） | R1 载体同一性 |
| **构建配置** | feature 组合、profile、优化等级、panic 策略、工具链版本、验证工具版本 | H4.1、R1 |
| **界声明** | AL2 证据的展开深度 / 形状约束 / 参数取值 | R2 |
| **参数化声明** | AL3 证据中哪些为参数、取值范围 | C3 参数化要求 |
| **时间与复现命令** | 完整可重跑命令 | 可复现性（§8.4） |
| **载体差异声明** | 验证对象与生产对象的**任何**差异，及其是否影响可观测行为 | R1 判定的直接依据 |

### 8.2 证据失效规则（本声明附加）

在 [MECHANISM.md](MECHANISM.md) M3.4（证据绑定源码变更）基础上，本声明补充：**以下变更同样使证据失效**，即使被验证的源码未变：

1. 验证工具或求解器版本变更（H1.2）；
2. 工具链版本变更（H1.1）；
3. 构建配置变更（H4.1）；
4. 依赖 crate 版本变更（H3.1、H3.2）；
5. 生产配置中的上界常量变更（C3）；
6. **载体同一性被破坏**：验证配置与生产配置之间出现新的行为级分叉（R1 —— 这类证据**应**降级为 AL2）。

### 8.3 超时与"未知"的处理

按规则 **R3**：

- 工具返回"未知 / 超时"**不得**记为通过；
- 该属性**应**在 [STATUS.md](STATUS.md) 中如实标注；
- 使用该属性的运行时行为**应**取向保守侧；
- 在声明的界内无法完成核验的验证单元，**应**被赋予明确的处置（分流至其他手段，或明确退役）。**"名义上存在、实质上无效"的验证单元不得计入任何声明的证据，也不得被引用。**

### 8.4 可复现性

EvoRule 采用"证据可重跑即证据"的原则：证据随仓发布（含元数据），任何第三方**应**能在受支持环境中重跑并得到相同结论。**未能重跑复现的证据，效力按降级处理。**

> **本附录为资料性**：应答解释的是本文件的**设计理由**，不含任何项目状态。凡涉及状态的追问，一律指向 [STATUS.md](STATUS.md)。

| **Q4** | 规格是谁写的？凭什么说规格符合意图？ | **结构性问题，任何等级都不覆盖**（规则 R4、NC-10）。形式化验证证明"实现符合规格"。规格可能遗漏你关心的性质。唯一缓解手段是外部独立审查（§9.1）与规格可读性，不是"更多证明"。 |

| **Q6** | 属性测试与差分测试只能证伪，为什么算证据？ | 它们**不计为证明**（AL1，非 AL3/AL4）。其价值在于：发现实现与规格的偏离，以及为无法穷尽的部分提供抽样证据。**凡以 AL1 支撑的性质，本文件已在 §3 各条的证据形式表中明确标注等级**，不与他人混淆。 |
| **Q7** | 证据绑定 commit，那么同一份源码在不同环境重跑，结论一致吗？ | 这是**可复现性的核心问题**。处置：证据必须记录完整环境元数据（工具链、验证工具、求解器版本、构建配置，§8.1），且**应**能被第三方重跑。求解器行为的不稳定性是已知风险（§9.1），因此**环境元数据与超时处置规则（R3）是证据效力的组成部分**。 |
| **Q8** | 你如何处理"求解器超时"？会不会把超时当通过？ | 明确禁止（规则 R3）。超时**不得**记为通过；系统在该属性上的运行时行为**应**取向保守侧。这条规则的方法论依据来自大规模求解实践（§9.1）。 |

| **Q13** | 二进制与源码一致吗？编译器会不会引入问题？ | 本文件**不主张任何目标码级别的性质保持**（NC-16）。AL4 的"逐字等同"针对**源码与构建配置**层；向交付二进制的延伸需要额外的编译链证据或二进制级验证，本文件不将其纳入保证范围。若某条声明确实具备该层证据，须先经 §0.6 B 类程序修订 NC-16 后方可主张。 |

| **Q15** | 如果依赖的密码学库有漏洞，你们的"不可篡改"声明是否失效？ | **是**（H3.1）。C4 的结构性质（篡改必然破坏链）不依赖库的具体实现强度；但"链不可被伪造"依赖哈希函数的抗碰撞性与签名实现正确性——这两项是**假设**，不是本仓可验证的性质（NC-7）。 |
| **Q16** | 你们列了 7 条声明。如果其中部分尚未达到目标等级，这算不算过度声明？ | **不算，因为声明与状态被强制分离。** 第 3 章定义**目标保证轮廓**（应达到什么程度），该定义不取决于当前达成情况；达成情况由 [STATUS.md](STATUS.md) 记录（M1），且任何对外材料只可引用其中已达成的项（M6）。二者不混同。**一个只声明"已达成部分"的文件无法指导后续工作；一个把目标说成现状的文件则是失实的。本文件选择前者，并通过 §0.4 的禁令使后者不可能。** |

## 结语

本文件的核心主张只有一句：**形式化验证的价值不在于用了什么工具，而在于对外承诺的内容被精确界定、证据强度被如实分级、验证对象被确认为交付物本身。**

因此，本文件把三件事写成硬条款：

1. **载体同一性**是等级判据，不是工程细节（规则 R1）；
2. **责任边界**必须明确，过度声明的代价高于少声明（§1.3、第 6 章）；
3. **规范与状态必须分离**：本文件规定**应达到什么**，[STATUS.md](STATUS.md) 记录**已达到什么**。**项目向本文件对齐，而非本文件向项目现状让步**（§0.4）。

第 3 条是本文件的效力基础。一份随项目进度频繁改动的承诺书不承担承诺功能——**承诺的稳定性是承诺有效性的前提**。因此本文件的修订只允许出于**自身缺陷**（§0.6）；项目向前推进、偏离被消除、证据被补足，都只改变 [STATUS.md](STATUS.md)，不改变本文件。
